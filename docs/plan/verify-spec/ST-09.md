- 관찰 가능한 계약:

  **`llm-match.ts`**
  - `LLM_MODEL = "claude-sonnet-5"`, `PROMPT_VERSION = "v2"`(라운드 1은 `"v1"` — 라운드 2에서 출력 스키마·프롬프트 변경에 맞춰 올림, 캐시 키에 포함되므로 옛 캐시와 절대 충돌하지 않음), `DEFAULT_MAX_DELTAS = 50`, `DEFAULT_MAX_TOTAL_CALLS = 60` (export).
  - `serializeCandidates(notes): string` — 후보 노트를 `{id,entity,skill,stat,before,after,direction,section}` 축약 뷰로 매핑 후 **id 오름차순 정렬**해 `JSON.stringify`. 타임스탬프·랜덤 없음 — 같은 노트 배열이면 호출 순서·횟수와 무관하게 바이트 단위로 동일(테스트로 고정, 프롬프트 캐싱 전제조건).
  - `candidateSetHash(serialized): string` — `sha256` hex.
  - `callLlmForDelta(client, model, delta, candidates): Promise<{parsed, usage}>` — **항상 실제로 API를 호출한다**(파일 캐시 확인 없음). `system`은 배열 1개짜리(`{type:"text", text, cache_control:{type:"ephemeral"}}`) — 후보셋 전체(patch의 전 노트, section 무관)를 담아 배치 내 모든 호출이 같은 prefix를 공유하게 한다. `messages.parse(...)`로 호출하고 `response.parsed_output`/`response.usage`를 그대로 반환(파싱 실패 시 `parsed_output=null`, 호출부가 가드).
  - `verifyCauses(rawCauses, candidates, delta, ddragon): LlmCause[]` — 3단 검증: ① `candidateNoteId===null`이면 그대로 `verified=false`. ② 후보 id 집합에 없으면 `candidateNoteId=null, verified=false`(텍스트/신뢰도는 보존). ③ 후보 id는 있지만 그 노트가 **델타 자신과 같은 엔티티**를 가리키면(챔피언은 `ddragon.champions.byKoName(note.entity)?.id===delta.entityKey`, 아이템은 `ddragon.items.byKoName(note.entity)`의 후보 배열 중 하나가 `String(id)===delta.entityKey`) `verified=false`로 폐기 — "이미 1단에서 다뤄졌어야 할 직접 변경을 2단이 재제시"하는 것을 막는다. 통과하면 `verified=true`.
  - **(라운드 2 신규) `verifySummaryCites(summaryCites, candidates): boolean`** — `summaryCites`의 모든 id가 입력 후보셋(id 집합)에 존재하는지만 확인한다. `causes`와 달리 **자기참조 배제는 요구하지 않는다**(summary가 델타 자신의 수치를 근거로 쓰는 것은 정상이므로 — S3 지시문 "델타 수치만 근거로 쓴 요약문은 summaryCites=[]"와 일치). 빈 배열은 "인용 없음"이라 항상 `true`.
  - `inferIndirectCandidates(deltas, notes, ddragon, options?): Promise<{deltas, summary}>` — 대상 필터: `status==="unannounced"||"announced-inconsistent"` 중 **입력 배열 순서 그대로(호출부가 이미 `sortDeltas`한 순서를 넘긴다고 가정 — 라운드 2에서 `run-match.ts`가 실제로 그렇게 하도록 고쳤다, 아래 "run-match.ts" 절 참고)** 상위 `maxDeltas`건. 대상이 아닌 델타는 그대로 통과(건드리지 않음). 각 대상 델타: 캐시 파일(`{cacheDir}/{sha256(model|promptVersion|deltaId|candidateSetHash)}.json`) 존재 → `cacheHits+=1`, API 호출 0, 캐시에 저장된 `parsed.causes`/`parsed.summaryCites`를 **현재 후보셋으로 재검증**(캐시 히트여도 `verifyCauses`/`verifySummaryCites`는 매번 다시 실행 — 안전망). 없음 + `calls>=maxTotalCalls` → `causes=[], llm:{skipped:true, reason:"call-budget-exceeded"}`(캐시 파일 안 씀). 없음 + 호출 가능 → `callLlmForDelta` 실행: 성공(`parsed!==null`) → 캐시 파일 기록 + `causes=verifyCauses(...)` + `llm:{skipped:false, summary: parsed.summary, summaryCites: parsed.summaryCites, summaryVerified: verifySummaryCites(parsed.summaryCites, notes)}`; `parsed===null`(스키마 파싱 실패) → `causes=[], llm:{skipped:true, reason:"parse-failed"}`(캐시 안 씀 — 다음 실행에서 재시도됨); 예외 발생 → `Anthropic.RateLimitError`는 `reason:"rate-limited"`, `Anthropic.APIError`는 `reason:"api-error-{status}"`, 그 외(예: API 키 자체가 없어 SDK가 네트워크 호출 전에 던지는 순수 `Error` — 라이브 실측, 아래 "실행 결과" 참고)는 `reason:"unknown-error"` — **어떤 경우도 throw하지 않고 해당 델타만 회색 처리한 뒤 나머지 델타 처리를 계속한다**(파이프라인 크래시 없음, 라이브 실측으로 확인).
  - `LlmRunSummary = {calls, cacheHits, skipped, usage:{inputTokens,cacheReadInputTokens,cacheCreationInputTokens,outputTokens}}` — `calls`는 **실제 API 호출 시도 횟수**(성공/실패 무관, 캐시 히트는 불포함), `skipped`는 세션 상한 초과로 아예 API를 호출하지 못한 델타 수(스키마 파싱 실패·API 에러로 인한 스킵은 `skipped`에 안 잡히고 `calls`에 잡힘 — "시도했지만 실패"와 "시도 자체를 안 함"을 구분).

- 구현 결정:
  - **캐시 히트 시에도 `verifyCauses`를 매번 재실행**한다(캐시된 `verified` 플래그를 그대로 믿지 않음) — 캐시 파일은 원시 LLM 응답(`parsed.causes`, 검증 전)을 저장하고, 검증은 항상 "현재 넘어온 `notes`/`delta`/`ddragon`" 기준으로 다시 계산한다. 캐시 키에 `candidateSetHash`가 포함돼 있어 이론상 항상 같은 후보셋이 들어오지만, 검증 로직 자체가 순수 함수라 재실행 비용이 거의 없고 방어적으로 안전하다.
  - **"call-budget-exceeded"(세션 상한)와 "parse-failed"/"rate-limited"/"api-error-*"(시도 후 실패)를 `LlmRunSummary`에서 구분**했다(`skipped` 카운터 vs `calls` 카운터) — PLAN이 "세션 상한... 나머지는 캐시만 사용" 이라고 명시했으므로, 상한 자체에 걸려 API를 아예 안 부른 것과, API를 불렀지만 실패한 것을 같은 숫자로 뭉치면 운영 중 원인 파악이 어려워진다고 판단했다.
  - **"1단에서 이미 매칭됐어야 할 노트를 2단이 재제시하는 경우"의 자기참조 판정을 `verifyCauses`에 내장**했다(별도 함수로 분리하지 않고 entity-match.ts와 동일한 `ddragon.champions.byKoName`/`ddragon.items.byKoName` 패턴을 재사용) — entity-match.ts의 로직을 import해서 재사용하는 것도 고려했으나, entity-match.ts는 "노트 집합 전체를 인덱싱"하는 배치 함수라 "노트 1건이 델타 1건과 같은 엔티티인가"라는 단건 질의에는 과하다고 판단해 llm-match.ts에 작고 독립적인 버전을 뒀다(로직은 동일, 코드는 별도 — 두 파일 다 F4 짝짓기 관련이라 완전한 중복 제거보다 각자 자기완결성을 택함).
  - **`inferIndirectCandidates`는 여전히 대상 델타를 스스로 `sortDeltas`하지 않는다(라운드 2에도 유지)** — 입력받은 `deltas` 배열의 순서를 그대로 신뢰해 앞에서부터 `maxDeltas`건을 자른다. 정렬 책임을 `inferIndirectCandidates` 내부로 옮기지 않고 **호출부(`runMatchPipeline`)가 정렬해서 넘기는 계약**을 택한 이유: `inferIndirectCandidates`는 llm-match.ts 소유 함수로 "정렬 우선순위"(`STATUS_SORT_PRIORITY`)라는 verdict.ts의 개념을 몰라도 되게 하는 편이 모듈 경계상 깔끔하고(llm-match.ts는 verdict.ts를 import하지 않는다 — 실제로 `sortDeltas`를 import하면 순환 의존 위험은 없지만 책임 소재가 흐려진다), `sortDeltas`가 이미 멱등(idempotent — 정렬된 입력을 다시 정렬해도 결과가 같음, `Array.prototype.sort`가 stable하므로)이라 호출부에서 한 번만 적용해도 충분하기 때문이다. **PLAN ①F4·PLAN③ST-09 행의 "상위 N건"** 요구를 이번 라운드에서 "중요도순(status 우선순위 → `|delta|` 내림차순) 상위 N건"으로 명확히 확정했다(라운드 1은 이 정의를 미확정으로 남겨뒀었다 — 위 개정 블록·미확인 사항 참고).
  - **`verifySummaryCites`가 `causes`의 자기참조 배제 로직(`resolvesToSameEntity`)을 재사용하지 않는다** — S3 지시문이 "델타 수치만 근거로 쓴 요약문은 summaryCites=[]"라고 명시해, summary는 causes와 달리 **델타 자신을 근거로 언급하는 것이 정상 케이스**이기 때문이다(예: "이전 대비 승률이 15%p 상승했습니다"는 후보 인용 없이도 유효한 요약). 따라서 `verifySummaryCites`는 순수하게 "존재하는 id인가"만 확인하고, `verifyCauses`처럼 "델타 자신의 엔티티를 가리키는 노트인지" 배제하지 않는다 — 오히려 summary가 델타 자신의 엔티티 변경 노트를 인용하는 것(1단에서 이미 다룬 직접 변경을 요약문 근거로 명시)은 자연스러울 수 있어(causes의 "간접 영향만 찾아라" 규칙과 summary의 "이 델타를 설명하라" 목적이 다름) 의도적으로 다른 검증 규칙을 뒀다.
  - `any` 미사용, `console`은 `scripts/run-match.ts`에서만 사용(진행 로그).

  - `data/cache/llm/`은 확인 결과 **디렉토리 자체가 생성되지 않았다**(`ls` exit 2) — 위 "키 없이" 스모크가 매번 API 호출 실패(`unknown-error`)로 끝나 `writeCache`(성공 시에만 호출)가 한 번도 실행되지 않았음을 실측으로 확인했다(코드 동작이 설계대로임을 검증 — 미확인 사항 아님으로 정정). **라운드 2에서 `PROMPT_VERSION`을 올렸으므로** 설령 라운드 1 실행으로 캐시 파일이 있었더라도 캐시 키가 달라져 자동으로 miss 처리됨 — 별도 캐시 무효화 작업 불필요(설계대로).
