- 구현 결정:
  - **`generateStaticParams`/`decodeIdParam` 히스토리 — 퍼센트 인코딩 반복 디코딩(1차) → `~` 슬러그 치환(2차 최종)**: 1차 구현은 `encodeURIComponent(id)`로 슬러그를 만들었는데, `npm run build`한 산출물의 RSC 페이로드를 열어보니 `params.id`가 `champion%3AQiyana%3ApickRate`가 아니라 `champion%253AQiyana%253ApickRate`(퍼센트 기호까지 한 번 더 인코딩된 상태)로 들어와 있었다 — Next.js 16.3.4가 정적 파라미터를 내부적으로 다시 한 번 `encodeURIComponent`하는 것으로 보인다. 1회 디코딩만으로는 `delta.id`와 대조가 실패해 모든 항목이 "데이터 없음"으로 렌더되는 문제가 있어, 처음엔 "더 이상 바뀌지 않을 때까지 반복 디코딩"으로 우회했다. **그런데 오케스트레이터가 이어서 배포 관점의 근본 문제(위 "관찰 가능한 계약" 참고 — 퍼센트 인코딩 자체가 정적 호스트에서 링크를 깨뜨림)를 확인하고 인코딩 방식 자체를 `itemSlug`(`:`↔`~` 문자 치환)로 바꾸라고 지시했다.** 슬러그에 애초에 `%`가 없으므로 Next.js의 "한 번 더 인코딩" 문제도 사라진다 — 그래도 `decodeIdParam`은 `decodeURIComponent` 1회를 방어적으로 유지한다(슬러그에 `%`가 없으니 대개 no-op이지만, Next.js가 라우트 파라미터를 인코딩해 넘길 가능성 자체를 배제할 수 없어 방어선으로 남긴다). 반복 디코딩 루프는 삭제했다(더 이상 필요 없음).
  - **동일 id가 여러 패치 쌍에 걸치는 문제**: `DeltaRecord.id` 포맷(`champion:{ddragonId}:{metric}` 등, types.ts 확정)엔 패치 쌍 정보가 없어 원리적으로 여러 쌍이 같은 id를 만들 수 있다(예: "26.16→26.17"과 "26.17→26.18" 둘 다 `champion:Trundle:pickRate`를 만든다). PLAN·UX-BRIEF 어디에도 이 충돌을 다루는 규칙이 없어, `listPatchPairs()`가 이미 최신 우선 내림차순을 보장한다는 점을 이용해 "가장 최신 쌍이 대표"로 단순하게 정했다(구현 결정, 별도 URL 네임스페이스 분리는 하지 않음 — PLAN이 쌍별 라우팅을 요구하지 않음).
  - **차트를 "전/후 2점 + CI 오차 막대"로만 구현(과제 지시가 이미 승인한 편차)**: 집계가 패치 단위라 일별 시계열 데이터가 없다. `ItemChart`는 recharts `BarChart`+`Cell`(전=`var(--fg-2)`, 후=`var(--accent)`)+`ErrorBar`(after 막대에만, `dataKey="error"`가 `[lowOffset, highOffset]` 오프셋 배열)로 구현했고, 부제로 "일별 추이는 수집 확장 후 제공"을 muted로 명시했다.
  - **오차 막대는 전/후 개별 CI가 아니라 델타(차이)의 CI 하나뿐**: `DeltaRecord`엔 `ci`(차이의 CI) 하나만 있고 전/후 각각의 Wilson CI는 저장되지 않는다(ST-08 확정 계약, `src/pipeline/match/delta.ts` 실장 확인). 그래서 after 막대의 오차는 `[delta-ci[0], ci[1]-delta]`(before를 기준으로 delta의 CI를 얹은 폭)로 계산했다 — self-pair 실측(delta=0, ci 대칭)으로 대칭성 검증(`chartData.test.ts`).
  - **통계 게이트 패널도 "관측 델타 CI(95%)" 한 줄만 표시**: 같은 이유(전/후 개별 CI 데이터 없음)로 프로토타입의 "Wilson 95% CI(전)"/"Wilson 95% CI(후)" 두 줄 대신 델타 CI 한 줄 + `q` + 승률이면 `WIN_RATE_MIN_N` 게이트 통과 여부(`passesSampleGate` 재사용)를 표시한다.
