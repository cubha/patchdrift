- 관찰 가능한 계약 (라운드 2 반영):
  - `collectSeedPuuids(client, {patch, tiers?, limit?, dataRoot?, nowMs?})` → `Promise<SeedResult>` where `SeedResult = {puuids: string[], createdAtMs: number}`(**개정**: 라운드1은 `Promise<string[]>`이었다). 순서: 챌린저→그랜드마스터→마스터, 티어 내부 `leaguePoints` 내림차순. 티어 간 중복 puuid는 먼저 등장한(더 높은 티어) 것만 남긴다. `data/raw/{patch}/seed-puuids.json`에 `{puuids, createdAtMs}`로 캐시하며 24시간 이내면 `getLeagueEntries` 재호출 없이 재사용한다 — 캐시 히트 시 `createdAtMs`는 "지금"이 아니라 캐시가 처음 만들어진 시각을 그대로 반환한다(crawler.ts가 재개 커서 유효성 판단에 쓴다). `limit`은 반환 배열만 자르고, 캐시 파일 자체는 항상 전체 집합을 저장한다.
  - `patchWindow(patch, nowMs?)` → `{startTime, endTime}`(epoch seconds). `startTime`=해당 패치 라이브(KST 00:00), `endTime`=다음 패치 라이브(캘린더에 다음 패치가 없으면 `nowMs()`). `PATCH_CALENDAR`에 없는 patch는 throw.
  - `crawlPatch(client, {patch, target, window?, idsPerPuuid?=100, maxPagesPerPuuid?=3, queue?=420, tiers?, seedLimit?, logEvery?=50, onProgress?, maxConsecutiveIdsFailures?=10, dataRoot?, nowMs?, signal?})` → `Promise<{collected, skippedVersion, skippedSeen, errors}>`(전부 "이번 실행" 기준 카운트, 누적치 아님). `maxConsecutiveIdsFailures`는 **신규 옵션**(라운드 2).
    - `target`은 패치 누적 목표치 — 실행 시작 시 `matches.jsonl` 기존 줄 수를 세어 이미 도달했으면 즉시 종료.
    - `window` 생략 시 `patchWindow(patch, nowMs)`로 계산(후보 축소용, 최종 컷은 `canonicalPatch(gameVersion) === patch`로만 판정).
    - seen-ids에 있는 matchId는 `getMatch` 호출 없이 `skippedSeen`으로만 센다.
    - `getMatch`가 `null`(404)이면 seen에 기록하고 skip(에러 아님). `canonicalPatch(gameVersion) !== patch`면 `skippedVersion`으로 세고 seen에 기록(재조회 방지). `toMatchSlim`이 throw하면(참가자/팀 수 불변식 위반) `errors`로 세고 seen에 기록(영구 결함으로 간주). `getMatch`가 네트워크성으로 throw하면 `errors`로 세되 seen에는 남기지 않는다(다음 실행 재시도 대상, 매치 단위 — crawler.ts:196-200).
    - **[개정] `getMatchIdsByPuuid`가 throw하면**(crawler.ts:169-182) `errors`+1 후 이 puuid를 "ids-failure"로 포기하고 다음 puuid로 계속 진행한다(같은 실행 내). 단, 이 puuid가 재개 커서 상의 "frozen 지점"이 되어 — 이후 다른 puuid가 성공적으로 끝나도 커서가 그 지점을 넘어가지 않는다(다음 실행에서 반드시 재시도된다). `getMatchIdsByPuuid`가 **연속** `maxConsecutiveIdsFailures`회(기본 10) 실패하면(성공 시 카운터 리셋) 키/네트워크 전반 문제로 간주해 크롤 전체를 즉시 중단하고 상태를 저장한다(crawler.ts:244-282).
    - 빈 배열 반환(더 조회할 매치가 없음)은 실패가 아니라 "매치 소진"이며 해당 puuid는 정상적으로 완료 처리된다(커서 전진 대상).
    - 컷 통과 매치는 `toMatchSlim()` 결과를 `matches.jsonl`에 동기 append(reduce-on-ingest)하고 matchId를 `seen-ids.txt`에 동기 append한다.
    - `target` 도달 또는 시드 puuid 소진 시 종료. `signal.aborted`가 되면 다음 매치/페이지/puuid 경계에서 즉시 멈춘다(append 구조라 별도 flush 불필요 — 이미 쓴 줄은 그대로 유효).
    - 진행 콜백 `onProgress({collected, target, seen, rateMatchesPerMin})`을 신규 수집 `logEvery`(기본 50)건마다, 그리고 종료 시 1회 호출한다. **crawler.ts/seed.ts/checkpoint.ts/patch-calendar.ts는 console을 쓰지 않는다** — 로그 출력은 `scripts/run-collect.ts`의 `onProgress` 구현에서만 한다.
    - **[개정] 재개(idempotent) 커서**: puuid 하나의 페이지 순회를 **완전히 마쳤을 때만**(마지막 페이지 도달 또는 `maxPagesPerPuuid` 도달, `processPuuidPages()`가 `"resolved"` 반환) 커서가 다음 puuid로 전진한다. `target` 도달·중단 신호·ids-fetch 실패로 중간에 멈추면 그 puuid에서 재개 지점이 고정된다(crawler.ts:284 `finalCursorIndex` 계산: `frozenIndex ?? i`, 단 시드가 통째로 소진되고 실패도 없었으면 `null`). 저장 위치는 `collect-state.json`의 `cursorPuuid`(puuid **값**, 인덱스 아님) + `seedCreatedAtMs`.
  - **[개정] `checkpoint.ts`** — `loadSeenIds`/`appendSeenId`(동기 append, 1줄 1 id), `countJsonlLines`/`appendJsonl`(동기 append), `loadCollectState`/`saveCollectState`(`{cursorPuuid: string | null, seedCreatedAtMs: number, updatedAtMs: number}` — 라운드1의 `{puuidIndex, updatedAtMs}`를 대체). 전부 `{patch, dataRoot?}` 형태의 `CheckpointPaths`를 받아 `dataRoot` 지정 시 `data/raw/{patch}/` 대신 `{dataRoot}/raw/{patch}/`를 쓴다(테스트 전용, `shared/paths.ts`는 수정하지 않았다 — `timeline.ts`가 쓰는 것과 동일한 관례).
  - `crawler.ts`의 `resolveStartIndex(puuids, cursorPuuid, storedSeedCreatedAtMs, currentSeedCreatedAtMs)` — `cursorPuuid===null`이면 0. `storedSeedCreatedAtMs !== currentSeedCreatedAtMs`(시드가 재생성됨)면 **`indexOf` 조회 없이 무조건 0**(재생성된 시드의 순서를 신뢰할 수 없으므로 — 결함 1의 핵심 수정). 그 외에는 현재 puuid 배열에서 `cursorPuuid`를 `indexOf`로 찾아 그 위치부터, 못 찾으면(시드에서 사라진 puuid) 0부터.
  - `scripts/run-collect.ts` — `npm run pipeline:collect -- --patch 26.17 --target 10000 [--tiers challenger,grandmaster] [--seed-limit N] [--dry-run]`. `--patch` 필수(없으면 throw) **및 `PATCH_CALENDAR`에 등록돼 있어야 함(개정 — `--dry-run`에도 적용)**, `--target` 기본 10000(양수 검증), `--tiers`는 `challenger|grandmaster|master` 콤마 목록(잘못된 값은 throw), `--dry-run`은 인자 검증만 하고 `loadEnv()`/클라이언트 생성 없이 종료. `SIGINT` 수신 시 `AbortController.abort()`로 `crawlPatch`에 중단 신호를 전달하고 정상 종료(run-collect.ts:112-117). `dispose()`는 `finally`로 항상 호출(run-collect.ts:137-140). 에러 로그(`main().catch`, run-collect.ts:143-146)는 `error.message`만 출력하며, `riot-client.ts`의 모든 throw 메시지는 `maskedUrl()`(쿼리스트링 제거)만 담고 API 키를 절대 포함하지 않는다(riot-client.ts의 throw 사이트 전수 확인 — 217/232/243/260/264/267/276/288/296/402/407행, 403 메시지는 정적 문자열).

- 구현 결정:
  - `seed.ts`/`crawler.ts`가 요구하는 `data/raw/{patch}/seed-puuids.json` 캐시 경로와 dataRoot 오버라이드는 PLAN ⑥의 데이터 계약에 없는 파일이라, `shared/paths.ts`를 수정하지 않고 각 모듈이 `rawDir(patch)`(읽기 전용 재사용)와 로컬 `path.join`으로 직접 구성했다 — `timeline.ts`(동시 작업 중인 다른 SubTask)도 동일한 패턴(`resolveMatchesJsonlPath`/`resolveTimelinesJsonlPath` + `dataRoot?`)을 쓰고 있어 관례가 일치한다.
  - `crawlPatch`의 반환값(`collected`/`skippedVersion`/`skippedSeen`/`errors`)은 "이번 실행" 기준이고, `onProgress`의 `collected`는 "누적"(이전 실행분 포함) 기준이다 — 서로 다른 의미의 두 숫자를 명확히 분리했다(누적 진행률 표시와 실행 단위 요약을 동시에 요구하는 스펙 문구를 그대로 만족).
  - 네트워크성 실패(`getMatchIdsByPuuid`/`getMatch`가 throw — 429/5xx/403 재시도 예산 소진 등 `riot-client.ts`가 이미 재시도한 뒤에도 실패한 경우)는 seen에 남기지 않아 재실행 시 자동 재시도되게 했다. 반면 404(`null`)·`gameVersion` 컷 탈락·`toMatchSlim` 불변식 위반은 "영구적 사실"로 보고 seen에 기록해 재조회를 막았다 — 배치 프롬프트가 명시한 "404·null은 seen 기록 후 skip"을 그대로 따르고, 이를 근거로 다른 영구 실패 사유(컷 탈락·데이터 손상)에도 같은 원칙을 확장했다.
  - `target`을 "이 실행에서 새로 모을 개수"가 아니라 "패치 누적 목표"로 해석했다(PLAN 문구 "패치당 목표 1만"과 정합) — 실행 시작 시 기존 `matches.jsonl` 줄 수를 세어 이미 달성했으면 즉시 0건으로 종료한다.
  - `collect-state.json`은 여전히 puuid(페이지/매치 단위 세분화는 하지 않음) 단위로만 재개 지점을 기록한다 — 다만 **[개정] "puuid 인덱스"가 아니라 "puuid 값"**을 저장한다(결함 1 수정). seen-ids가 이미 매치 단위 dedup을 보장하므로, 재개 시 앞쪽 페이지를 다시 조회하는 API 비용만 감수하면 정확성엔 문제가 없다는 원래 판단은 유지하되, "앞쪽 페이지 재조회"의 범위가 라운드 2에서 "시드가 재생성된 경우 전체 재조회"로 넓어졌다(안전 우선 — 부분 재조회 최적화보다 정확성을 우선).
  - **[신규 결정] "frozen 커서" 개념**: `getMatchIdsByPuuid` 실패는 "이번 실행에서 다음 puuid로 넘어가는 것"과 "다음 실행에서 재개할 지점"을 분리해야 한다 — 전자는 처리량을 위해 계속 진행하고, 후자는 실패한 지점에 고정해야 그 puuid가 영구히 스킵되지 않는다. 스코프-크리틱 원문은 "해당 puuid 커서는 전진하지 말 것"이라고만 명시했지만, 이는 사실상 전역 커서 1개만 존재하는 구조에서 "이후 puuid가 성공해도 커서가 실패 지점을 넘지 못하게 한다"는 뜻으로 해석해야만 의미가 성립한다(그렇지 않으면 뒤이은 성공한 puuid가 커서를 전진시켜 실패한 puuid를 결국 놓친다) — 이 해석에 따라 `frozenIndex`를 도입했다.
  - **[신규 결정] 연속 실패 임계치의 범위**: `maxConsecutiveIdsFailures`는 `getMatchIdsByPuuid`(매치ID 목록 조회) 실패만 센다 — 리뷰 원문이 이 엔드포인트를 명시했기 때문이다. `getMatch`(매치 상세) 실패는 기존처럼 매치 단위로만 `errors`에 누적되고 서킷브레이커에는 반영하지 않는다(같은 근본 원인이라도 매치 상세 실패는 이미 "seen에 안 남김 → 자동 재시도"로 각 매치 단위 복원력이 있어, 별도 카운터를 또 두면 두 실패 유형이 상호작용해 조기 중단 임계치 계산이 더 불투명해진다는 판단). 오케스트레이터가 두 실패군을 합산한 서킷브레이커를 원하면 별도 SubTask로 확장 필요.
  - `run-collect.ts`의 인자 파서는 의존성 추가 없이 수작업 `switch` 파서로 구현했다(배치 프롬프트 "간단 argv 파서, 의존성 추가 금지"). `--dry-run`의 `PATCH_CALENDAR` 검증(라운드 2 추가)도 이 파서 안에서 처리해 `crawlPatch` 호출 없이도 조기 실패하게 했다.
  - stub/fallback 없음 — ST-03 범위(시드·크롤러·체크포인트·CLI)는 전량 구현했다. `--dry-run`은 요구사항에 명시된 정식 기능이지 임시 스텁이 아니다.

- 미확인 사항:
  - 실제 라이브 크롤(D+1 게이트, PLAN 배치 순서 "▶ 운영")은 이번 배치 범위 밖이다 — 이 SubTask는 가짜 `RiotClient`로만 검증했고, 실제 Riot API 응답으로 `crawlPatch`가 패치당 2,000~10,000건을 실제로 채우는지는 오케스트레이터가 별도로 `npm run pipeline:collect -- --patch 26.17 --target 10000`을 백그라운드 실행해 확인해야 한다.
  - `patch-calendar.ts`의 라이브 일자(KST 00:00 가정)는 배치 프롬프트가 준 값을 그대로 옮긴 것이며, 실제 배포 시각(수요일 새벽~오전)과의 오차가 시간창 후보를 얼마나 좁히는지는 실측하지 않았다 — 최종 컷은 `gameVersion` 비교로 하므로 정확도에는 영향 없으나, 오차가 크면 `getMatchIdsByPuuid` 페이지네이션에서 이전 패치 매치가 다수 섞여 `skippedVersion` 비율이 높아질 수 있다(실크롤 시 관찰 필요).
  - `maxPagesPerPuuid`(기본 3, puuid당 최대 300개 매치ID 후보)가 목표 1만 건 달성에 충분한지는 라이브 실측이 필요하다 — 시드 puuid 수(챌린저 299 + GM/마스터, ST-02 실측)와 티어당 실제 해당 패치 기간 랭크 게임 수에 따라 부족하면 `--seed-limit` 없이 전체 시드를 쓰거나 `maxPagesPerPuuid`를 늘려야 할 수 있다.
  - **[라운드 2 신규]** `maxConsecutiveIdsFailures`(기본 10)의 실제 값이 라이브 환경에 적절한지는 실측하지 않았다 — 429는 `riot-client.ts`가 이미 최대 5회 재시도 후 throw하므로, 리밋 초과가 아주 짧게(몇 초) 발생해도 크롤러 레벨에서 10번 연속 실패가 쌓이면 전체 중단될 수 있다. 실크롤에서 정상적인 일시적 리밋 스파이크로 오탐 중단되는지 관찰이 필요하다.
  - **[라운드 2 신규]** 시드 재생성 시 "전체 재시작"(인덱스 0부터) 정책은 안전하지만 puuid 수가 많을수록(챌린저 299+) 재개 시 API 비용이 커진다 — `getMatchIdsByPuuid` 자체는 매번 다시 호출되기 때문이다(seen-ids는 매치 상세 재조회만 막지 목록 조회 자체는 막지 못함). 실크롤에서 하루 여러 번 재시작하는 운영 패턴이면 이 비용이 유의미한지 관찰이 필요하다 — 필요하면 "puuid별 마지막 처리 완료 시각"까지 caching하는 후속 최적화를 별도 SubTask로 고려할 수 있다(이번 배치 범위 밖).
