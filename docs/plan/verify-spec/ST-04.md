- 관찰 가능한 계약:
  - `reduceTimeline(match: MatchSlim, raw: RiotMatchTimelineDto): TimelineSlim` — 순수 함수(부수효과 없음).
    - `lanes`: `TOP`/`JUNGLE`/`MIDDLE`/`BOTTOM`/`UTILITY` 각각에 대해 `match.participants`에서 `teamId===100`(blue)·`teamId===200`(red) & 해당 `teamPosition`을 가진 참가자를 찾고, `participantId = index+1`로 `raw.info.frames[*].participantFrames[String(participantId)].totalGold`를 읽는다. 10분값은 `timestamp >= 600_000`인 첫 프레임, 14분값은 `timestamp >= 840_000`인 첫 프레임에서 읽고, 해당 프레임이 없거나 참가자를 못 찾으면 `null`. 양쪽 다 못 찾은 포지션은 `lanes`에서 키 자체를 생략(`Partial<Record<LanePosition, TimelineLaneSplit>>`).
    - `firstObjectives`: 모든 프레임의 `events`를 순서대로 순회해 `ELITE_MONSTER_KILL`(`monsterType`: `"DRAGON"`→`dragonSec`, `"RIFTHERALD"`→`heraldSec`, `"BARON_NASHOR"`→`baronSec`)와 `BUILDING_KILL`(`buildingType==="TOWER_BUILDING"`)→`towerSec`의 최초 발생 `timestamp`를 초 단위(`Math.floor(ms/1000)`)로 기록. 해당 타입 이벤트가 없으면 `null`. `HORDE`(void 유충)·`ATAKHAN`(방장 몬스터) 등 계약 외 `monsterType`은 무시.
    - 경기가 10/14분 미만이면 해당 골드·오브젝트 값이 `null`로 남을 뿐 매치를 skip하지 않는다(`TimelineSlim` 타입이 이미 `null`을 허용).
  - `sampleMatchIds(jsonlPath: string, k: number, seed = DEFAULT_TIMELINE_SAMPLE_SEED): string[]` — `matches.jsonl`을 읽어 `matchId` 목록을 얻고, mulberry32 시드 PRNG 기반 Fisher-Yates 셔플 후 앞에서 `k`개를 반환. 같은 `(jsonlPath, k, seed)`는 항상 같은 결과(순서 포함)를 반환. `k`가 전체 개수 이상이면 전체(순서는 셔플됨)를 반환. 파일이 없으면 빈 배열.
  - `collectTimelines(client: RiotClient, {patch, sample, seed?, dataRoot?, onProgress?}): Promise<{written, skipped, nulls, errors}>`:
    - `matches.jsonl`(경로는 `dataRoot` 주어지면 `{dataRoot}/raw/{patch}/matches.jsonl`, 아니면 `shared/paths.ts`의 `matchesJsonl(patch)`)에서 `sampleMatchIds`와 동일한 시드 셔플로 `sample`개를 뽑는다.
    - `timelines.jsonl`(같은 규칙, `timelinesJsonl(patch)`)에 이미 존재하는 `matchId`는 `client.getMatchTimeline`을 호출하지 않고 `skipped`로 집계(idempotent 재개). 성공적으로 append된 matchId만 "이미 수집됨"으로 취급 — `null`/에러로 끝난 matchId는 다음 실행에서 재시도 대상이다(의도적 설계, 아래 "구현 결정" 참고).
    - `getMatchTimeline`이 `null`(404)을 반환하면 `nulls` 집계, 예외를 던지면 `errors` 집계(둘 다 진행은 계속). 성공하면 `reduceTimeline` 후 JSONL 한 줄로 append하고 `written` 집계.
    - 진행 상황은 `onProgress?: (event: {matchId, index, total, status: "written"|"skipped"|"null"|"error", error?})` 콜백으로만 노출한다 — 함수 내부에 `console.*` 호출 없음(요구사항: "console은 scripts만").
  - `scripts/run-timeline.ts --patch <PatchId> --sample <n> [--dry-run]`:
    - `--patch` 필수(없으면 throw), `--sample` 기본값 1500, 양수가 아니면 throw.
    - `--dry-run`이면 `loadEnv()`만 수행하고 네트워크 호출 없이 인자만 로그 후 종료.
    - 정상 실행: `loadEnv()` → `createRiotClient({apiKey, platform:"kr", region:"asia"})`(ST-02 계약 그대로, `smoke-riot.ts`와 동일 라우팅) → `collectTimelines` → 요약 로그 → `finally`에서 `client.dispose()`(리소스 누수 방지, ST-02 계약과 동일).
    - env 값(API 키 등)은 어떤 로그에도 출력하지 않는다.

- 구현 결정:
  - **null/error는 "미수집"으로 남긴다(skip 대상 아님)**: `skipped` 판정은 오직 `timelines.jsonl`에 이미 성공 기록된 matchId에만 적용한다. Riot API가 일시적으로 404/5xx를 반환한 매치를 영구히 건너뛰면 표본이 조용히 줄어들기 때문에, 재실행 시 자동 재시도되도록 설계했다(PLAN F1 idempotent 재개 원칙과 동일 취지를 F8에 적용). `errors` 카운트가 반복해서 늘어나면 호출자(운영자)가 로그로 원인을 판단한다.
  - **`dataRoot?` 오버라이드는 `shared/paths.ts`를 건드리지 않고 로컬에서 흡수**: `matchesJsonl`/`timelinesJsonl`(`shared/paths.ts`, 다른 에이전트 동시 작업 대상이라 수정 금지 지시)은 `DATA_ROOT=process.cwd()/data`를 하드코딩한다. 테스트에서 임시 디렉토리를 쓰기 위해 `collectTimelines`/내부 헬퍼가 `dataRoot`가 주어지면 `path.join(dataRoot, "raw", patch, "matches.jsonl"|"timelines.jsonl")`를 직접 구성해 `shared/paths.ts`와 동일한 레이아웃 규칙을 로컬 재현했다. **계약 변경 없음**(paths.ts 미수정) — 다만 두 곳에 같은 경로 규칙이 존재하게 되므로, 추후 paths.ts가 `dataRoot` 파라미터를 공식 지원하게 되면 이 로컬 헬퍼는 제거하고 위임하는 것이 바람직하다(인접 경계 참고).
  - **결정론적 표본에 외부 의존성 미도입**: `seed` 기반 셔플은 mulberry32(순수 JS, 의존성 0)로 구현했다. `package.json`에 이미 없는 난수 라이브러리를 추가하지 않기 위함. 시드값·알고리즘은 이 파일에만 있으므로 향후 다른 SubTask가 같은 방식의 표본이 필요하면 이 함수를 재사용해야 한다(현재는 export하지 않는 내부 `seededSample`이지만 필요 시 export 검토).
  - **오브젝트 초 단위는 `Math.floor(ms/1000)`**: 반올림 대신 내림을 택했다 — "그 시각까지 몇 초가 지났는가"를 나타내는 지표라 올림/반올림보다 내림이 보수적이고 직관적이라 판단(advisor 상담 없이 결정 — 단일 파일 스코프의 계산 규칙이라 CLAUDE.md "생략 가능: 원인이 명확한 버그 수정·기존 패턴 따르는 구현" 범주로 판단, 값 자체의 유의성은 집계 단계(ST-06)의 평균 계산에서 ±1초 이내로 무시 가능).
  - **`reduceTimeline`은 프레임이 정렬돼 있다고 가정**: Riot match-v5 timeline 응답은 항상 `frames[].timestamp` 오름차순이다(ST-02 라이브 실측·본 배치 실측 모두 확인). 방어적 재정렬은 하지 않는다 — 만약 향후 비정렬 응답이 관측되면 별도 결함으로 다뤄야 한다(미확인 사항에도 기록).
  - **fixture 구성 방식**: `riot-timeline-26-17.json`은 실제 라이브 스모크 응답(`data/raw/samples/timeline.json`, gitignore 대상)에서 3개 프레임만 남기고, 오브젝트 이벤트(HORDE·TOWER·DRAGON·RIFTHERALD, 실제 timestamp 그대로)는 편의상 마지막 프레임의 `events` 배열에 모아 담았다 — `reduceTimeline`은 이벤트가 속한 프레임 인덱스가 아니라 이벤트 자신의 `timestamp` 값만 사용하므로 결과 정확성에 영향 없음(테스트 파일 상단에 동일 주석 명시). 실제 매치엔 `BARON_NASHOR` 킬이 없어(20분 만에 종료) 이 경로는 fixture로 검증하지 못했고, 별도 synthetic 객체 리터럴(테스트 내 인라인)로 baron 탐지·오브젝트별 최초값-only 보장·짧은 경기(10/14분 프레임 없음) 3가지 케이스를 보강했다.
  - stub/fallback 없음. `console.log`는 `scripts/run-timeline.ts`에서만 사용(verify.sh 규칙 준수, `timeline.ts`는 `onProgress` 콜백만 노출).

- 미확인 사항:
  - `ELITE_MONSTER_KILL`의 `monsterType` 실측값 중 `BARON_NASHOR`는 이번 배치에서도 라이브로 관측하지 못했다(ST-02 스모크 매치·본 배치가 재사용한 fixture 매치 모두 20분 내 종료). PLAN 배치 프롬프트와 Riot 문서 상 문자열이 `"BARON_NASHOR"`라는 점은 업계 표준 문서 기준으로 채택했으나, 실제 라이브 응답으로 재확인된 적은 없다 — D+2 게이트(26.17→26.18 각 2,000매치) 실수집 시 최소 1건 이상의 바론 이벤트로 문자열을 검증해야 한다.
  - `frames[].timestamp`가 항상 오름차순이라는 가정은 지금까지의 실측(ST-02·본 배치) 2개 매치로만 확인했다 — 표본 규모(1,500매치)에서 예외가 있는지는 실수집 전까지 알 수 없다.
  - `collectTimelines`가 `sample` 개수만큼 순회하는 동안 Riot API 리밋(ST-02의 bottleneck 체인)에 걸려 느려지는 실제 처리 시간은 측정하지 않았다 — PLAN 운영 계획(D+1 게이트)의 "수집 3.3h/패치"가 상세 수집(ST-03) 기준인지 타임라인까지 포함한 수치인지 PLAN 문서에 명시가 없어 확인이 필요하다.
  - `package.json`의 `pipeline:*` 스크립트 목록에 `pipeline:timeline`(또는 `pipeline:all` 체인에 타임라인 수집 포함 여부)을 추가할지는 이번 배치 소유 파일 밖이라 손대지 않았다 — ST-14(배포·운영) 또는 통합 배치에서 결정 필요.
