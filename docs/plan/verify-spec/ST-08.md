- 관찰 가능한 계약:

  **`ddragon.ts`**
  - `loadDdragon(version?: string, options?: {dataRoot?: string}): DdragonData` — `data/ddragon/{version}/{champion,item}.json`(scripts/run-ddragon.ts가 받아둔 로컬 파일)을 읽는다. **네트워크 호출 없음** — `version` 생략 시 `dataRoot/ddragon/` 아래 다운로드된 버전 디렉토리 중 semver 내림차순 최신을 고른다. 데이터가 없으면 `run-ddragon.ts 실행` 안내 문구를 포함한 에러.
  - `DdragonData = { version, champions: {byKey(numericId), byId(ddragonId), byKoName(koName)}, items: {byId(itemId), byKoName(koName): DdragonItem[], isCompleted(itemId)} }`. **`items.byKoName`은 단일 값이 아니라 배열을 반환한다**(PLAN 예시 객체 리터럴엔 없었지만, 실측으로 게임 모드 간 이름 충돌이 있어 이 배치에서 추가한 API — 아래 구현 결정 참고). `champions.byKoName`은 단일 값(챔피언명은 충돌 없음, 실측 확인).
  - `isCompletedItem({into, gold, tags})`: `into.length===0 && gold.purchasable && gold.total>=1600 && tags에 Boots/Consumable/Trinket 없음`. `COMPLETED_ITEM_MIN_GOLD=1600`로 export.
  - `normalizeKoName(s)`: 공백·중점(`·`/`ㆍ`/`・`)·따옴표류 제거 + NFKC. **순서 중요**: 중점 제거를 NFKC 정규화보다 먼저 해야 한다 — NFKC가 `ㆍ`(U+318D)를 `ᆞ`(U+119E)로 바꿔버려 정규화 후에 지우면 원래 문자 클래스가 못 잡는다(테스트로 회귀 고정).

  **`scripts/run-ddragon.ts`**

  - `collectAppearedEntities(dataRoot?)`: `data/aggregated/*/`(`deltas`·`notes` 디렉토리 제외) 전 패치를 스캔해 `championId`/`itemId` 합집합을 모은다(패치 여러 개가 쌓여도 한 번에 전부 커버).
  - 이미지: 등장한 championId/itemId만 `cdn/{v}/img/{champion,item}/{...}.png` → `public/dd/{champion,item}/`, 이미 있으면 skip(동시성 6). 룬 아이콘(`img/perk-images/...`)은 **다운로드하지 않는다** — 현재 파이프라인에 룬 단위 통계 집계 엔티티가 없어(패치노트 `subsection:"rune"` 분류는 있지만 ST-06 집계 대상은 챔피언/아이템뿐) 다운로드할 대상 자체가 없다(미확인 사항에 재기록).
  - 콘솔 출력: 버전·등장 엔티티 수·이미지 다운로드/스킵/실패 건수·매핑 실패 목록·완성템 수.

  **`delta.ts`**
  - `AggregatedPatch = {patch, champions: ChampionStat[], items: ItemStat[], lanes: LaneGoldStat[], objectives: ObjectiveStat, summary: PatchSummary}`. `loadAggregatedPatch(patch, dataRoot?)`가 `data/aggregated/{patch}/*.json` 5종을 읽어 반환 — 파일이 없으면 `run-aggregate.ts --patch {patch}` 실행을 안내하는 에러로 **즉시** 실패(파이프라인 중간에서 애매하게 죽지 않도록 — advisor 권고 반영).
  - `buildDeltas(before, after, {ddragon, dataRoot?}): DeltaRecord[]`. 반환 레코드는 **아직 패치노트와 짝지어지지 않은 중간 상태**다: `status`는 전부 `"no-change"`(자리표시자, verdict.assignStatus가 최종 덮어씀), `matchedNoteId`/`matchedNoteIds`/`causes`는 항상 비어있다.
  - **측정 불가 케이스는 레코드 자체를 생략**(0으로 얼버무리지 않음 — CLAUDE.md "무근거=회색" 원칙의 연장): 라인 골드@14는 `n14===0`인 쪽이 있으면 스킵, 오브젝트는 `mean===null`인 쪽이 있으면 스킵, 매치 평균은 `matches===0`인 쪽이 있으면 스킵, 챔피언은 `before`에 그 챔피언 자체가 없으면(신규 챔피언) 스킵, 라인은 그 포지션 표본이 아예 없는(행 없음) 쪽이 있으면 스킵. **반대로** 픽률/밴률/채택률/승률은 분모(totalMatches/totalParticipants)가 항상 존재해 n=0이어도 "진짜 0%"인 유효한 값이므로 항상 레코드를 만든다 — 승률의 표본 부족 여부는 verdict가 `insufficient-sample`로 판정하지, delta.ts가 생략하지 않는다.
  - **챔피언 포지션 행이 한쪽에만 있으면**(그 포지션 n=0), 챔피언 자체는 양쪽에 존재한다는 전제(`scope=all` 행 존재) 하에 없는 쪽을 진짜 0(픽 0회)으로 간주해 델타를 만든다 — "그 포지션에서 완전히 밀려남/새로 채용됨"이라는 유효한 신호이기 때문(구현 결정, 아래 상세).
  - **id/entityKey 네임스페이스(ST-08 확정, types.ts DeltaRecord 헤더 주석과 동일)**: `champion:{ddragonId}:{metric}`(scope=all, metric∈{pickRate,banRate,winRate}) | `champion:{ddragonId}:{pos}:{metric}`(scope=position, metric∈{pickRate,winRate} — 밴은 포지션이 없어 이 포맷에 없음) | `item:{itemId}:adoptionRate` | `lane:{position}:{goldAt10|goldAt14}` | `objective:{dragon|herald|baron|tower}`(metric은 항상 `"firstSec"`) | `summary:avgDurationSec`. **`entityKey`는 항상 챔피언/포지션 무관 ddragon id(예: "Aatrox") 하나로 고정** — 포지션별 메트릭도 entityKey를 공유해야 entity-match가 "엔티티 단위로 하나의 노트 묶음"을 만들 수 있기 때문(포지션은 id에만 나타나고 metric·entityKey에는 안 나타남).
  - **밴/승 원시 카운트 역산(구현 결정)**: `ChampionStat`은 `banRate`/`winRate`(비율)만 저장하고 원시 횟수를 안 남긴다(ST-06 계약) — `Math.round(rate * totalMatches|n)`으로 역산해 Newcombe CI/p값의 입력(successes, trials)으로 쓴다. 픽률은 raw `n`(정확한 정수)이 있어 역산 없이 그대로 쓴다. 아이템 채택률도 raw `n`/`totalParticipants`가 있어 역산 없음.
  - **연속 지표 p값 로컬 구현(구현 결정, 배치 경계 준수)**: `meanDiffPValue(mean1,sd1,n1,mean2,sd2,n2)`(z=diff/se, 양측)는 `stats.ts`(ST-05 소유)에 없어 이 파일에 로컬로 뒀다 — `erf`/`normalCdf` 근사를 `stats.ts`와 동일한 방식으로 **의도적으로 중복 구현**했다(배치 지시가 허용한 수정 범위는 `types.ts` 1개뿐이라 ST-05 소유 파일을 건드리지 않기 위함). 코드에 이 사유를 명시했다.
  - **`aggregatePath` 프래그먼트 형식(구현 결정 — PLAN이 "`#rows[...]`" 형식만 지정, 세부는 이 배치가 확정)**: 챔피언 `#rows[championId={id},scope=all]` 또는 `#rows[championId={id},scope=position,position={pos}]`, 아이템 `#rows[itemId={id}]`, 라인 `#rows[position={pos}]`, 오브젝트 `#data.{name}`, 매치 평균 `#data.avgDurationSec`. 항상 **after 패치** 파일을 가리킨다(before/after 두 패치 중 "지금 관측된 상태"를 가리키는 쪽).
  - **원천 매치 ID 표본(성능, advisor 지적 반영)**: `sampleMatchIdsByEntity(matchesJsonlPath, championIds, itemIds)`가 `matches.jsonl`을 **단일 스트리밍 패스**로 읽어 관심 엔티티별 최대 10개 matchId를 모은다. 엔티티마다 파일을 재스캔하면 수백 엔티티 × 수천 매치로 느려지므로(실측 26.17 기준 3,405줄·15MB, 계속 증가 중) 반드시 이렇게 구현했다. 라인/오브젝트/매치평균 레코드의 `evidence.matchIds`는 항상 `[]`(PLAN이 "엔티티가 등장한 매치" 표본을 요구한 대상은 챔피언/아이템뿐 — 라인/오브젝트는 매치 전체에 걸친 지표라 개별 엔티티-매치 대응이 없음).
  - **BH-FDR은 buildDeltas가 만든 전체 델타 목록에 공통 적용**한다(`benjaminiHochberg(drafts.map(d=>d.p), FDR_ALPHA)`) — champion/item/lane/objective/summary 전 지표를 한 번에 다중비교 보정.

  **`entity-match.ts`**
  - `matchDeterministic(notes, deltas, ddragon): {matches: Map<deltaId, {noteIds, directionAgreement}>, mappingFailures: string[]}`. `section==="champion"|"item"`인 노트만 블로킹 대상(system/other는 애초에 챔피언/아이템 엔티티가 아니라 제외). 매핑 실패(ddragon에 없는 한글 엔티티명)는 `mappingFailures`에 정렬·중복제거해 담는다(PLAN "매핑 실패 목록을 반환(보고에 포함)" 대응 — ddragon.ts 자체는 note 입력을 받지 않으므로 이 매핑은 entity-match.ts 몫으로 배치했다, 아래 구현 결정 참고).
  - **엔티티 단위 노트 묶음**: 같은 `entityType:entityKey`를 가진 델타는 전부 같은 노트 묶음(`noteIds`)을 공유한다 — `entityKey`가 포지션 무관 챔피언 id로 고정된 delta.ts 설계 덕에 별도 그룹핑 로직 없이 Map 키만으로 달성된다.
  - **방향 정합**: 노트 방향 다수결(`buff`/`nerf` 카운트, `adjust`/`unknown`은 기권) vs 관측 델타 부호(양수=`up`, 음수=`down`, 0/null=`flat`). `noteDirection==="neutral"`(동률·전부 adjust/unknown) 또는 `observed==="flat"`이면 `"neutral"`, 그 외 일치하면 `"consistent"` 불일치면 `"inconsistent"`.
  - **밴률 방향 규칙(구현 결정)**: PLAN이 명시한 건 "픽률·승률·채택률 상승=+"뿐이고 밴률은 언급이 없다 — 이 배치는 밴률도 동일하게 "상승=긍정 반응(buff 쪽)"으로 균일 처리한다(밴률 전용 반전 규칙 없음). 실제 게임 밸런스에서 버프가 밴률 상승과 반드시 같은 방향이라는 보장은 없지만(오히려 하향된 챔피언의 밴률이 하락하는 게 자연스러움), PLAN이 별도 규칙을 주지 않아 임의로 반전 로직을 추가하지 않았다 — 미확인 사항에 재기록.
  - **아이템 이름 충돌 처리**: `ddragon.items.byKoName(entity)`가 배열을 반환하므로 후보 전부에 노트를 걸어둔다(예: "폭풍갈퀴" 노트는 SR 완성템 id와 아레나 변형 id 둘 다에 걸림) — 실제 델타가 있는 쪽만 자연히 매칭되고 없는 쪽은 그냥 미사용 버킷으로 남아 무해하다(실측: 26.17 아레나 변형 id는 우리 집계에 애초에 등장하지 않음).

  **`verdict.ts`**
  - `assignStatus(delta, match): MatchStatus`. 판정 순서(advisor 권고대로 n 게이트를 유의성 표보다 먼저 확인 — PLAN ②가 "미달=insufficient-sample"을 무조건 조항으로 서술):
    1. `metric==="winRate" && !passesSampleGate(n.before, n.after)` → **무조건** `"insufficient-sample"`(노트 매칭·유의성과 무관).
    2. 유의(`q<FDR_ALPHA(0.10) && CI가 0을 포함하지 않음`): 노트 짝 있음 → 방향 `consistent`면 `"announced-consistent"`, 그 외(`inconsistent`/`neutral`)면 `"announced-inconsistent"`; 노트 짝 없음 → `"unannounced"`.
    3. 비유의: 노트 짝 있음 → `"announced-inconsistent"`(노트는 변경을 말했지만 통계적으로 유의한 변화가 관측되지 않음); 노트 짝 없음 → `"no-change"`(ST-08 신규 상태 — "잡음 델타"를 "미공지 변화"와 구분, types.ts에 정의 추가).
    - **`passesSampleGate`는 `metric==="winRate"`일 때만 적용**한다 — 픽률/밴률/채택률/라인골드/오브젝트/매치평균은 이 게이트 대상이 아니다(PLAN "승률 델타는 n≥200 게이트..."가 승률에만 적용됨을 명시).
  - `applyVerdicts(deltas, matchOutcome, notesById): DeltaRecord[]` — 불변(입력 배열 복사), `status`/`matchedNoteId`(대표=noteIds[0])/`matchedNoteIds`/`evidence.noteAnchor`(매칭된 노트의 `anchorUrl`, 없으면 `null`)를 채운 새 배열 반환.
  - `sortDeltas(deltas)`: status 우선순위(`unannounced`=0 > `announced-inconsistent`=1 > `announced-consistent`=2 > `insufficient-sample`=3 > `no-change`=4) → 동순위는 `|delta|` 내림차순(`delta===null`은 `-Infinity` 취급해 맨 뒤).
