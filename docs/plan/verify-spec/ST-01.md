### VERIFY-SPEC — SubTask ST-01

- 기준선 요구사항: "도메인 타입·패치 매핑·경로·env 로더 확정 — `PatchId` 양방향 매핑(26.17↔16.17), `parseGameVersion`, data 레이아웃 상수, zod env 스키마" (PLAN ③ ST-01 행). 배치 프롬프트 원문: `types.ts`는 MatchSlim/ParticipantSlim/TimelineSlim/ChampionStat/ItemStat/ObjectiveStat/LaneGoldStat/PatchSummary/PatchNoteItem/DeltaRecord/MatchStatus/LlmCause/Verdict 계약을 확정, `patches.ts`는 canonicalPatch/toDdragonMajor/parseGameVersion, `paths.ts`는 PLAN ⑥ 경로 그대로, `env.ts`는 dotenv+zod(RIOT_API_KEY 필수, ANTHROPIC_API_KEY·DISCORD_WEBHOOK_URL 선택, PATCH_FROM/PATCH_TO 기본 26.16/26.17)이며 값을 절대 로그하지 않는다.

  - `src/pipeline/types.ts` (수정 — 도메인 타입 계약 확정/확장)

- 관찰 가능한 계약:
  - `canonicalPatch("16.17.708.1234")`/`canonicalPatch("16.17.1")`/`canonicalPatch("26.17")` → 모두 `"26.17"`. 판별 기준은 세그먼트 개수가 아니라 major 크기(`major < 20` → gameVersion/ddragon 표기로 보고 `+10`, 아니면 이미 패치노트 표기).
  - `toDdragonMajor("26.17")` → `"16.17"`. major<20 입력(이미 ddragon 표기로 보이는 값)은 throw.
  - `parseGameVersion("16.17.708.1234")` → `{major:16, minor:17, canonical:"26.17"}`.
  - 형식이 `major.minor[...]`가 아니면(빈 문자열·숫자 세그먼트 1개 이하 등) 세 함수 모두 throw.
  - `rawDir/matchesJsonl/timelinesJsonl/seenIdsFile/aggregatedDir/deltasFile/notesFile/llmCacheDir`는 PLAN ⑥ 문자열 그대로 — 특히 `seen-ids.txt`(하이픈, `seenIds.txt` 아님), `deltas/{from}_{to}.json`, `notes/{patch}.json`, `cache/llm`.
  - `loadEnv(source?)`: source 생략 시 `.env` 파일을 로드한 뒤 `process.env`를 검증(스크립트 진입점용), source 지정 시 dotenv 로드를 건너뛰고 주어진 객체만 검증(테스트 주입 — `.env` 파일 유무에 의존하지 않는다). `RIOT_API_KEY` 없으면 throw(메시지는 필드 경로만 포함, 수신값 노출 없음). `PATCH_FROM`/`PATCH_TO` 미지정 시 각각 `"26.16"`/`"26.17"`.

- 구현 결정:
  - `MatchSlim.participants`/`teams`는 길이 10/2 불변식을 타입(튜플)이 아니라 `toMatchSlim()`(ST-02)의 런타임 검증으로 강제한다 — 튜플 캐스팅은 실제 보장을 주지 않는다는 판단(advisor 합의).
  - `ChampionStat`은 기존 필드(championId/championKey/position/patch/n/pickRate/banRate/winRate) 위에 `championName`·`ci: {pick, ban, win|null}`을 추가하는 방식으로 확장했다(이름 유지 원칙).
  - `ItemStat`은 기존 4필드(itemId/patch/n/adoptionRate)에 `ci: Interval` 1개만 추가했다 — 챔피언별 세분화는 PLAN 문구에 근거가 없어 임의 추가하지 않음(ST-06에서 필요하면 확장).
  - **계약 변경(기존 스텁 대비)**: 기존 `ObjectiveStat`은 `lane`·`goldAt10`·`goldAt14`를 포함했으나, 신규 `LaneGoldStat`으로 그 책임을 이전하고 `ObjectiveStat`은 순수 오브젝트(용/전령/바론/포탑 첫 획득 평균 시각)만 남겼다. `aggregate/objectives.ts`(ST-06 소유)는 이 변경을 반영해 시그니처를 조정해야 한다.
  - `DeltaRecord`는 PLAN 배치 프롬프트가 지정한 신규 필드 세트(`entityType/entityKey/entityName/metric/before/after/delta/ci/n/q/status/matchedNoteId/causes/evidence`)로 전면 교체했다 — 기존 스텁의 `patchFrom/patchTo/entity/deltaAbs/ciLow/ciHigh/patchNoteItemId/verdict` 필드는 제거됐다. `match/verdict.ts`·`match/entity-match.ts`(ST-08)·`discord/webhook.ts`(ST-13)는 타입만 참조하는 스텁이라 컴파일은 깨지지 않았지만, 실제 구현 시 새 필드셋을 따라야 한다.
  - `Verdict` 타입은 하위호환을 위해 그대로 보존했다(기존 필드 무변경). `Verdict.sourceUrl/reasoning`(무근거=null 렌더 규칙)과 신규 `DeltaRecord.status/evidence/causes`가 개념적으로 겹친다 — ST-08이 `verdict.ts`를 구현할 때 `Verdict`를 `DeltaRecord`에 어떻게 통합할지(별도 필드로 유지 vs `DeltaRecord`만으로 대체) 확정이 필요하다.
  - env.ts는 zod `.strict()`를 쓰지 않는다 — `process.env`는 수백 개 키를 갖고 이 프로젝트의 실제 `.env`도 `RIOT_PERSONAL_KEY`/`RIOT_DEV_KEY` 등 스키마 외 키를 갖기 때문(기본 strip 모드로 무시).
  - stub/fallback/하드코딩 없음. "나중에 제대로" 보류 항목 없음 — ST-01 범위(타입·매핑·경로·env)는 전량 구현 완료.

- 인접 경계:
