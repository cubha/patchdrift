  **✅ types.ts 승격 완료 — 공식 계약(5개 인터페이스 필드 확장, 이번 후속 지시로 반영)**

  1. **`ChampionStat`에 `scope: "all" | "position" | "unknown"` 판별자와 `totalMatches: number`를 추가했다.**
     - `scope="position"`: 명명된 포지션(TOP/JUNGLE/MIDDLE/BOTTOM/UTILITY) 1개에서의 등장(픽/승) 통계. `position` 필드가 그 포지션 값.
     - `scope="unknown"`: `teamPosition===""`(미배정·비표준 케이스)인 등장 통계. `position=""`.
     - `scope="all"`: 챔피언 전체(포지션 무관) 합산 — 챔피언당 정확히 1행. `position=""`.
     - (1차 구현 때는 `""`가 "미배정"과 "합산" 두 의미를 동시에 져서 `ChampionStat`만 보는 소비처가 오독할 위험이 있었다 — advisor 검토로 지적됐고, `scope`를 3-way로 승격해 완전히 해소했다. `position` 필드 자체의 의미는 `scope="position"`일 때만 유효하고 나머지는 `""`로 고정된다.)
     - `totalMatches`는 `pickRate`/`banRate`의 공통 분모(해당 패치 전체 매치 수)를 행 단위로 자기완결시킨 값.
  2. **`ChampionRateCi.ban: Interval | null`, `ChampionStat.banRate: number | null`로 nullable화했다.** 밴은 포지션 정보가 없는 챔피언 단위 지표라 **`scope==="all"`인 행에만 값이 있고, `scope==="position"`/`"unknown"` 행은 항상 `null`이다.** 1차 구현 때는 모든 행에 동일 값을 복제해 "ST-08이 같은 밴을 여러 행에서 중복 합산할 위험"이 있었는데, 이제는 계약 자체가 그 실수를 원천 차단한다(포지션 행에서 밴을 읽으면 `null`이 나오므로 코드가 자연히 실패/스킵한다).
  3. **`ItemStat`에 `totalParticipants: number`를 추가했다** — `n`(보유자 수, 분자)만 있고 분모가 없던 문제 해소. `adoptionRate = n / totalParticipants`이며 ST-08의 Newcombe 채택률 델타 CI 계산에 바로 쓸 수 있다.
  4. **`LaneGoldStat`에 `goldAt10Sd: number`·`goldAt14Sd: number`·`n14: number`를 추가했다.** `goldAt14Avg`는 여전히 non-nullable이라 `n14===0`이면 `summarize([])`의 `mean=0`이 그대로 들어갈 수 있다 — **소비처는 반드시 `n14`을 먼저 확인한 뒤에만 `goldAt14Avg`를 신뢰해야 한다**(이 한계는 타입 자체의 non-null 제약에서 오는 것이라 이번 승격으로도 완전히는 못 없앴다 — types.ts 주석에 명시). `goldAt10Avg`는 행 자체를 `n===0`일 때 생략하므로 안전.
  5. **`ObjectiveStat`에 `dragon`/`herald`/`baron`/`tower: ObjectiveMetricDetail`(신규 export, `{n, mean: number|null, sd, occurrenceRate}`)을 추가했다.** `ObjectiveStat.n`은 오브젝트 종류와 무관한 **표본(타임라인) 전체 수**(`timelines.length`)이고, 개별 오브젝트의 실제 발생 건수(`n`)·표본표준편차(`sd`)·발생 비율(`occurrenceRate`)은 하위 필드에 있다.
  6. **`PatchSummary`에 `avgDurationSecSd: number`·`queueDistribution: Record<number, number>`·`gameCreationMsRange: {min,max}|null`·`timelineSamples: number`를 추가했다**(PLAN ST-06 원문이 요구한 "평균 경기 시간(초·sd), 큐 분포, 수집 시각 범위, 타임라인 표본 수" 그대로).

  **ST-08/ST-10을 위한 소비 가이드(더 이상 "확장 인터페이스를 알아야 하는" 문제가 아니라 base 타입 자체의 필드 사용 규칙)**
  - 챔피언 밴 델타는 `champions.filter(r => r.scope === "all")`에서만 읽는다(포지션/미배정 행은 `banRate`/`ci.ban`이 `null`이라 애초에 값이 없다).
  - 챔피언 포지션별 픽/승 델타는 `scope === "position"`만, 미배정 등장 비중을 따로 보고 싶으면 `scope === "unknown"`을 쓴다.
  - 아이템 델타 CI는 `n`과 `totalParticipants`를 함께 쓴다.
  - 라인 골드 @14 델타 전에 `n14 > 0`을 확인한다(0이면 값이 없다는 뜻).
  - 오브젝트 발생 비율·sd가 필요하면 `objectives.dragon.occurrenceRate` 등 하위 필드를 쓴다(`ObjectiveStat.n`은 발생 건수가 아니라 전체 표본 수).
  - 매치 평균 카드에 sd·큐 분포·수집 범위·타임라인 표본 수가 필요하면 `PatchSummary`의 해당 필드를 그대로 쓴다(더 이상 별도 타입 import 불필요).

  **집계 규칙**
  - `aggregateChampions`: 명명된 포지션 중 `n>0`인 것만 `scope="position"` 행(0-픽 포지션 행은 생략). `teamPosition===""` 등장이 있으면 `scope="unknown"` 행을 별도로 낸다. 챔피언별로 정확히 1개의 `scope="all"` 행이 항상 존재 — 픽 기록이 전혀 없이 밴만 된 챔피언도 `n=0`인 ALL 행으로 나타난다(이름은 `""` — 아래 "밴 전용 챔피언 이름" 참고). `pickRate = n/전체매치수`, `banRate`(=all 행만) `= 밴매치수(팀 중복 제거)/전체매치수`, `winRate = 승수/n`(n=0이면 0). `ci.pick`은 항상 Wilson, `ci.ban`은 all 행만 Wilson(그 외 null), `ci.win`은 `n>=WIN_RATE_MIN_N(200)`일 때만 Wilson(미만은 null). 정렬: `pickRate` 내림차순, 동률은 `championName`→`position`→`scope` 오름차순(포지션·scope 모두 같은 경우는 원천적으로 존재하지 않지만 완전한 결정론을 위해 3단 비교를 둔다).
  - `aggregateItems`: 참가자당 `items[0..5]`(6슬롯, `item6` 장신구 제외) 중 `itemId>0`인 것만, 참가자 내 중복 슬롯은 1회로 dedup 후 카운트. `adoptionRate = n/totalParticipants`(matches.length*10과 동일값, participants 배열 실측 합). 완성템 필터링(6슬롯 중 실제 "완성"인지 여부)은 하지 않는다 — PLAN에 "완성템 필터는 ST-08 Data Dragon 단계 몫"이라 명시된 지시를 그대로 따름. 정렬: `adoptionRate` 내림차순, 동률은 `itemId` 오름차순.
  - `aggregateLanes`: `LANE_POSITIONS` 5종 고정 순서로 순회, `blue`/`red` 구분 없이 참가자 단위 값 풀링. `goldAt10`/`goldAt14` 각각 `null` 제외 후 `stats.summarize()`. **`goldAt10` 표본이 0(n===0)인 포지션은 행 자체를 생략**한다(가짜 0 값이 ST-08 델타 비교를 오염시키는 것을 방지. 실측: `data/raw/26.17`은 아직 timelines.jsonl이 없어 `lanes.json`의 `rows`가 `[]`).
  - `aggregateObjectives`: `dragonSec`/`heraldSec`/`baronSec`/`towerSec` 각각 `null` 제외 평균·sd, `occurrenceRate = 비null건수/timelines.length`(timelines가 0건이면 0).
  - `summarizePatch`: `matches`(matches.length), `avgDurationSec`/`avgDurationSecSd`(matches의 gameDurationSec 기반, matches=0이면 둘 다 0), `firstXSecAvg`(timelines 기반, timelines=0이거나 전부 null이면 null), `queueDistribution`(queueId→건수), `gameCreationMsRange`(matches=0이면 null), `timelineSamples`(timelines.length).
  - 밴 전용(픽 기록 없음) 챔피언 이름: `championName=""`(빈 문자열). "UNKNOWN" 같은 표시 문자열을 그대로 UI에 흘리지 않기 위한 결정 — championId는 있으므로 ST-08의 Data Dragon 매핑 단계에서 이름을 복원할 수 있다.
  - `championKey`: 현재는 raw `championName`을 그대로 사용(Data Dragon slug 매핑은 아직 없음 — ST-08 몫).

  **`run-aggregate.ts` CLI — 출력 JSON 스키마 (ST-08·ST-10 소비용, 5개 파일 전부 `data/aggregated/{patch}/` 아래)**
  - `npx tsx scripts/run-aggregate.ts --patch <PatchId> [--data-root <dir>]`. `--data-root`는 `shared/paths.ts`를 건드리지 않고 ST-04(`collect/timeline.ts`)와 동일한 패턴(로컬에서 `path.join(dataRoot, ...)` 재해석)으로 테스트 격리를 지원한다.
  - `matches.jsonl`/`timelines.jsonl`을 라인 단위로 읽어 `JSON.parse` 실패 라인은 카운트만 하고 skip한다(크롤러가 append 중일 때 마지막 줄이 잘려 있는 경우 대비). 파일이 없으면 빈 배열(에러 아님).
  - 5개 파일 공통 `meta`: `{ patch: PatchId, generatedAt: string(ISO 8601), nMatches: number, nParticipants: number, nTimelines: number, source: "riot-match-v5" }`.
  - **`champions.json`** → `{ meta, rows: ChampionStat[] }` — 필드: `championId, championKey, championName, position, patch, scope, totalMatches, n, pickRate, banRate, winRate, ci:{pick,ban,win}`.
  - **`items.json`** → `{ meta, rows: ItemStat[] }` — 필드: `itemId, patch, n, totalParticipants, adoptionRate, ci`.
  - **`lanes.json`** → `{ meta, rows: LaneGoldStat[] }` — 필드: `patch, position, n, goldAt10Avg, goldAt10Sd, goldAt14Avg, goldAt14Sd, n14`.
  - **`objectives.json`** → `{ meta, data: ObjectiveStat }`(단일 객체) — 필드: `patch, n, firstDragonSecAvg, firstHeraldSecAvg, firstBaronSecAvg, firstTowerSecAvg, dragon, herald, baron, tower`(각 `{n, mean, sd, occurrenceRate}`).
  - **`summary.json`** → `{ meta, data: PatchSummary }`(단일 객체) — 필드: `patch, matches, avgDurationSec, avgDurationSecSd, firstDragonSecAvg, firstHeraldSecAvg, firstBaronSecAvg, firstTowerSecAvg, queueDistribution, gameCreationMsRange, timelineSamples`.
  - `objectives`/`summary`가 `rows`가 아니라 `data`인 것은 PLAN이 "`{meta, rows}` 또는 타입이 요구하는 형태"로 유연성을 허용했고, 이 둘은 배열이 아닌 단일 객체 개념(`ObjectiveStat`/`PatchSummary`)이기 때문이다.
  - `JSON.stringify(value, null, 2)` + 개행 1줄, `fs.mkdirSync(recursive:true)`로 `data/aggregated/{patch}/` 생성.
  - `main()`은 `import.meta.url === pathToFileURL(process.argv[1]).href` 가드 뒤에서만 실행되므로(node:url 기반, 문자열 단순 연결 아님) 테스트에서 이 파일을 import해도 부수효과(파일쓰기·process.exit)가 없다 — `loadJsonl`/`parseArgs`를 직접 단위 테스트했다.

- 구현 결정:
  - **1차 구현(로컬 상위집합 인터페이스 우회)에서 이번 후속 지시(types.ts 승격)로 전환한 이유**: 당시엔 `types.ts`를 동시편집하는 다른 에이전트가 있어 수정이 금지돼 있었다. 편집 충돌이 해소된 뒤 "우회로를 정식 계약으로 승격하라"는 코디네이터 지시를 받아, `ChampionStatRow`/`ItemStatRow`/`LaneGoldStatDetail`/`ObjectiveStatDetail`/`PatchSummaryDetail` 5개 로컬 인터페이스를 완전히 삭제하고 그 필드를 `types.ts`의 `ChampionStat`/`ItemStat`/`LaneGoldStat`/`ObjectiveStat`/`PatchSummary`에 그대로 병합했다. 필드명은 1차 구현 때 verify-spec에 문서화한 이름(`totalMatches`, `totalParticipants`, `goldAt10Sd`/`goldAt14Sd`/`n14`, `dragon`/`herald`/`baron`/`tower`, `avgDurationSecSd`/`queueDistribution`/`gameCreationMsRange`/`timelineSamples`)을 그대로 유지했다 — 재설계가 아니라 승격이기 때문에 이름을 바꿀 이유가 없었다.
  - **`ChampionStat.scope`를 2-way(`"position"|"all"`, 미배정은 `scope="position"&&position=""`로 표현)에서 3-way(`"position"|"all"|"unknown"`)로 재설계했다** — 코디네이터가 후속 지시에서 명시적으로 `scope:'all'|'position'|'unknown'`을 요구했고, 이렇게 하면 `position` 필드는 `scope==="position"`일 때만 의미를 갖는 것으로 완전히 단순해진다(1차 구현의 "position=''가 all과 unknown을 동시에 표현" 문제가 근본적으로 사라진다). 이에 맞춰 `champions.ts`의 `makeRow`가 `scope` 인자만으로 `ci.ban`/`banRate`를 null화할지 결정하도록 재작성했다.
  - **`banRate`/`ci.ban`을 nullable로 계약에 편입**해 "포지션 행에서 밴을 중복 집계하는 footgun"을 타입 레벨에서 차단했다 — 1차 구현은 문서(verify-spec)로만 경고했지만, 이번 승격에서는 `scope!=="all"`이면 값 자체가 `null`이라 잘못 합산하면 `null`과의 산술 연산에서 TypeScript가 즉시 컴파일 에러를 낸다(방어가 문서에서 타입 시스템으로 이동).
  - `lanes.ts`의 기존 `classifyLane`/`Lane` export는 저장소 전체 grep으로 무참조를 확인한 뒤 완전히 삭제하고 파일을 새 목적(`aggregateLanes`)으로 재작성했다(1차 구현과 동일 — 이번 후속 지시로 바뀐 부분 없음).
  - `objectives.ts`의 함수 시그니처를 `(timelineSampleFile: string, patch)`(파일 경로 입력)에서 `(timelines: TimelineSlim[], patch)`(이미 로드된 배열 입력)로 바꾼 것도 1차 구현과 동일 — I/O를 `run-aggregate.ts`(스크립트 계층)로 밀어내고 `aggregate/*`는 순수 함수만 남긴다는 프로젝트 디렉토리 규칙을 따름.
  - `betaBinomialShrink`(stats.ts, ST-05가 이미 구현)는 이번에도 **사용하지 않았다** — ST-06 지시문이 `winRate = 승/등장(n)`(원시 비율)로 명시했고, 이번 후속 지시에도 축소 언급이 없어 반영하지 않았다(미확인 사항에 유지).
  - `any` 미사용, `console`은 `scripts/run-aggregate.ts`에서만 사용(진행 로그 3줄). 테스트 픽스처(`__tests__/fixtures.ts`)는 1차 구현과 동일하게 손으로 합성한 `MatchSlim`/`TimelineSlim` 빌더를 사용(개별 케이스마다 다른 조합이 필요해 raw fixture 1개로는 부족).

- 미확인 사항:
  - `betaBinomialShrink` 미적용(위 구현 결정 참고) — ST-08이 저표본 챔피언 랭킹에서 왜곡을 문제 삼으면 `champions.ts`에 축소 필드를 추가해야 한다(이 경우 `ChampionStat`에 또 필드 추가가 필요하므로 types.ts 재개정 필요).
  - `LaneGoldStat.goldAt14Avg`가 `n14=0`일 때 `0`을 반환하는 문제(non-nullable 타입 제약)는 이번 승격에서도 완전히 해소하지 못했다 — `goldAt14Avg`를 `number | null`로 바꾸는 것이 근본 해결이지만 이번 후속 지시 범위(스코프·밴 null화·5개 필드 승격)에는 포함되지 않아 보류했다. 소비처가 `n14`을 확인하지 않으면 실측 없는 0을 실제 값으로 오독할 수 있다는 리스크는 그대로 남아 있다.
  - `championKey`가 raw `championName`(예: Riot 내부 표기 그대로)이라 Data Dragon 키(실제 slug)와 다를 수 있는 챔피언이 있는지는 확인하지 못했다 — ST-08의 엔티티 블로킹(`ko 이름↔ddragon key`) 단계에서 별도 정규화가 필요할 수 있다.
  - 밴 전용 챔피언(픽 기록 0)이 실데이터에 존재하는지는 아래 실행 시점(1,379매치) 기준으로 확인하지 않았다(수집이 계속 진행 중) — 로직 자체는 합성 테스트로 커버.
  - `ChampionStat.scope`를 3-way로 승격하면서 `position` 필드가 `scope!=="position"`일 때 사실상 사용되지 않는(`""` 고정) 필드가 됐다 — 장기적으로는 `position`을 `scope==="position"`일 때만 존재하는 discriminated union으로 다듬는 편이 더 엄격하지만, 이번 지시 범위(기존 필드 유지 + 확장)에서는 하지 않았다.
