- 관찰 가능한 계약:

  **`webhook.ts`**
  - `buildBriefingEmbeds(deltas: DeltasFile, options: BuildBriefingOptions): DiscordEmbed[]` — 항상 **embed 정확히 1개**를 담은 배열을 반환한다(≤10 요구는 구조적으로 항상 만족 — 분리 로직 없음).
    - `BuildBriefingOptions = { siteUrl: string; topN?: number(기본 5); noteCount?: number | null; matchCounts?: { from: number | null; to: number | null } }`. `noteCount`/`matchCounts`는 `DeltasFile`에 없는 값(패치노트 고유 엔티티 수·매치 수)이라 호출부가 별도 로드해 주입하는 additive 옵션이다 — 생략 시 헤드라인의 "패치노트는 N개 엔티티를 말했고" 구간 자체를 생략하고, footer는 `n=?/?`로 표시한다(무근거로 지어내지 않음, CLAUDE.md 원칙 연장).
    - `title`: `"patchgap · {from} → {to}"`. `url`: `siteUrl` 그대로. `color`: `0x38bdf8`(--accent 토큰 값의 정수 변환, 코드에 `design-lint-ignore` 주석).
    - `description`: `"{패치노트는 N개 엔티티를 말했고, }통계는 {M}개 변화를 말합니다 · 미공지 {U}건{ · 게이트를 통과한 미공지 변화 없음}"`(ST-11 `HeroSummary`와 통일된 문구, 후속 지시 1 반영). U는 `rows.filter(status==="unannounced").length`. M(유의 변화 개수)은 `status`가 아니라 `q`/`ci`/게이트를 직접 재판정해 계산한다 — **ST-11의 `statCount`(status 기반: announced-consistent+announced-inconsistent+unannounced)와 다른 정의다**, 아래 구현 결정에서 이유와 두 화면 간 수치 불일치 가능성을 설명한다. 필드가 잘려나가면(아래) `" · …외 k건"`을 이어붙인다.
    - `fields`: `status==="unannounced"` 상위 `topN`건(경고 표시 없음) + `status==="announced-inconsistent"` 상위 3건(이름 앞에 `"⚠ "`). 각 필드 `name = "{entityLabel} · {metricKo}"`, `value = "{formatDeltaLine} · [근거]({siteUrl}/item/{encodeURIComponent(id)}/)"`(+검증된 원인 텍스트 또는 `"근거 미확인"` 줄, 원인이 아예 없으면 그 줄 자체 생략).
    - `footer.text`: `"patchgap · n={nFrom}/{nTo} · {generatedAt(KST)}"`. `generatedAt`은 `deltas.meta.generatedAt`을 `lib/format.fmtKst`로 변환.
    - **제한 강제**: 필드 ≤25, `name`≤256/`value`≤1024(개별 truncate, 말줄임 `…`), 총 문자수(title+description+footer.text+Σ(name+value)) ≤6,000 — 필드를 채우기 **전에** `"…외 k건"` 접미사용 예산(24자)을 먼저 떼어두고 그리디로 채운다(뒤늦게 붙이면 상한을 넘길 수 있다는 advisor 지적 반영).
    - `formatDeltaLine(d: DeltaRecord): string` — export된 순수 헬퍼. `metric`이 `pickRate|banRate|winRate|adoptionRate`면 비율(%, %p, CI는 ×100 스케일 후 `±X`), `goldAt10|goldAt14`면 정수(`fmtInt`/`fmtDeltaInt`), 그 외(`firstSec`·`avgDurationSec`)면 초(`fmtSec`/`fmtDeltaSec`) 포맷 — 전부 `src/lib/format.ts` 헬퍼 재사용(이 파일은 `server-only`를 import하지 않아 파이프라인에서 안전하게 소비 가능함을 확인, 아래 구현 결정 참고). `before/after/delta` 중 하나라도 `null`이면 `"데이터 없음"`.
  - `sendWebhook(url: string, payload: DiscordWebhookPayload, options?: SendWebhookOptions): Promise<SendWebhookResult>` — `SendWebhookOptions = { fetchImpl?, sleepImpl?, maxRetries?(기본 3) }`, `SendWebhookResult = { status: number; retries: number }`.
    - POST `{ "Content-Type": "application/json" }` + `JSON.stringify(payload)`(`payload.username==="patchgap"`).
    - `200|204` → 즉시 성공 반환(`retries`=그때까지의 실패 횟수).
    - `429` → 바디 JSON의 `retry_after`(초, 소수 허용) 우선, 실패 시 `Retry-After` 헤더(초), 그마저 없으면 지수 백오프(`500ms * 2^attempt`) — 대기 후 재시도. `attempt(현재까지의 시도 횟수)`가 `maxRetries`에 도달하면 그 자리에서 throw.
    - `5xx` → 지수 백오프 재시도, 동일하게 `maxRetries` 도달 시 throw.
    - 그 외 4xx(429 제외) → **즉시** throw(재시도 없음). 에러 메시지는 `status`와(있으면) 응답 바디 앞 200자만 담고, **`url` 문자열은 어떤 에러 메시지에도 절대 포함하지 않는다**(웹훅 URL 자체가 토큰이라 riot-client.ts의 "쿼리스트링만 제거하는 마스킹"으로는 부족 — 완전 배제).
    - `maxRetries` 의미: "429·5xx가 공유하는 총 시도 횟수 상한"(재시도 횟수가 아니고, 429/5xx 각각 별도 예산도 아니다 — 하나의 `attempt` 카운터를 공유한다) — `maxRetries=3`이면 3번째 시도까지 실패 시 그 자리에서 throw(총 3회 `fetchImpl` 호출). riot-client.ts는 429/5xx를 `retries429`/`retries5xx` 별도 카운터로 관리하고 "MAX_ATTEMPTS=재시도 횟수(첫 시도 제외)"인데, 이 파일은 둘 다 다르다(아래 구현 결정에서 이유 설명).

  **`run-notify.ts`**
  - `parseArgs(argv): RunNotifyArgs = { from, to, top(기본5), site(기본 DEFAULT_SITE_URL 상수), dryRun(기본false) }` — `--from`/`--to` 필수, `--top`은 양의 유한수여야 함, 미지정 인자는 에러. **후속 지시 3**: `site`(기본값이든 `--site`로 명시했든 최종 값 기준)가 trim 후 빈 문자열이면 에러, `/^https?:\/\//i`에 매치하지 않으면(스킴 없음·`ftp://` 등) 에러 — `DEFAULT_SITE_URL` 자체는 항상 이 검사를 통과하므로 `--site` 미지정 시엔 동작 변화 없음.
  - `loadDeltasFile(from, to, dataRoot = DATA_ROOT): DeltasFile` — `{dataRoot}/aggregated/deltas/{from}_{to}.json` 없으면 `run-match.ts` 실행을 안내하는 에러(delta.ts `loadAggregatedPatch`와 동일한 "즉시 실패" 원칙).
  - `loadNoteCount(patch, dataRoot = DATA_ROOT): number | null` — `{dataRoot}/aggregated/notes/{patch}.json`을 전체 파싱해 `countEntityNotes(items)`(아래)로 계산한다. **`meta.itemCount`(전체 노트 줄 수, system/other 포함)를 쓰지 않는다**(후속 지시 1 반영). 파일 없으면 `null`.
  - `countEntityNotes(items: readonly PatchNoteItem[]): number` — export된 순수 헬퍼. `section`이 `champion`|`item`인 항목만 대상으로 `${section}:${entity}` 키 중복 제거 후 개수를 센다(ST-11 `src/components/home/logic.ts`의 `countRelevantNoteEntities`와 동일 규칙, 이 배치에 로컬 재구현).
  - `loadMatchCount(patch, dataRoot = DATA_ROOT): number | null` — `{dataRoot}/aggregated/{patch}/summary.json`의 `data.matches`. 파일 없으면 `null`.
  - **`dataRoot` 파라미터(후속 지시 2로 셋 다 추가)**: `shared/paths.ts`(ST-01 소유)의 `deltasFile`/`notesFile`/`aggregatedDir`는 `DATA_ROOT`에 고정돼 있어 테스트 격리에 쓸 수 없다 — `src/pipeline/match/delta.ts`의 `loadAggregatedPatch(patch, dataRoot = DATA_ROOT)` 패턴을 그대로 따라, 세 함수 모두 `paths.ts` 헬퍼를 호출하지 않고 `path.join(dataRoot, "aggregated", ...)`를 직접 조립한다(`paths.ts` 자체는 수정하지 않음).
  - `loadDiscordWebhookUrl(source: Partial<NodeJS.ProcessEnv> = process.env): string`(후속 지시 2, 신규) — `DISCORD_WEBHOOK_URL` 하나만 요구하는 소형 zod 스키마(`z.object({ DISCORD_WEBHOOK_URL: z.string().min(1) })`)로 검증한다. **`src/pipeline/shared/env.ts`의 `loadEnv()`(RIOT_API_KEY 필수)를 더 이상 import하지 않는다** — `run-notify.ts`에서 `loadEnv` 참조가 완전히 사라졌다.
  - `runNotify(args: RunNotifyArgs, deps: RunNotifyDeps = {}): Promise<RunNotifyResult>`(후속 지시 2, 신규 — `main()`에서 분리) — `RunNotifyDeps = { fetchImpl?, env?, dataRoot? }`, `RunNotifyResult = { dryRun: boolean; embeds; send?: { status, retries, logFile } }`. 흐름: `loadDeltasFile`/`loadNoteCount`/`loadMatchCount`(전부 `deps.dataRoot` 사용) → `buildBriefingEmbeds` → 본문 문자수 콘솔 로그 → **`args.dryRun`이면 payload를 stdout에 출력하고 `{dryRun:true, embeds}` 반환 — `deps.env`를 전혀 읽지 않고 종료**(핵심 수정) → 아니면 `loadDiscordWebhookUrl(deps.env ?? process.env)` → `sendWebhook(url, payload, {fetchImpl: deps.fetchImpl})` → `writeNotifyLog({from,to,sentAt,status,retries}, dataRoot)` → `{dryRun:false, embeds, send:{status,retries,logFile}}` 반환.
  - `main()`: 이제 `parseArgs(process.argv.slice(2))` + 헤더 콘솔 로그 + `runNotify(args)` 호출만 남은 얇은 진입점(의존성 주입 없이 실제 `process.env`/`fetch`/`DATA_ROOT` 사용).
  - `isMainModule` 가드(run-match.ts/run-aggregate.ts와 동일 패턴) — import만으로 `main()`이 실행되지 않는다.

- 구현 결정(위에서 다루지 않은 것):
  - **"유의 변화 M개"를 `status`가 아니라 `q`/`ci`/게이트로 직접 재판정한다** — ST-08 `assignStatus`는 "유의+노트짝(불일치/중립)"과 "비유의+노트짝 있음"을 둘 다 `announced-inconsistent`로 합쳐 넣기 때문에(verdict.ts), status만으로는 "통계적으로 유의한 변화가 몇 건인가"를 구분할 수 없다. `isSignificant(row, qAlpha) = status!=="insufficient-sample" && q!==null && q<qAlpha && !(ci[0]<=0 && ci[1]>=0)`로 로컬 재정의했다(advisor 검토 반영).
  - **`noteCount`/`matchCounts`를 `BuildBriefingOptions`에 옵션으로 추가했다** — 오케스트레이터 지시의 헤드라인/footer 문구가 요구하는 값이 `DeltasFile` 스키마(ST-08/09 확정)에 전혀 없다(meta에는 `from/to/generatedAt/n(=rows.length)/counts/qAlpha/llm?`뿐). `webhook.ts`를 순수하게 유지하기 위해(파일 I/O 없이 결정론적으로 테스트 가능) 이 두 값을 호출부가 읽어 주입하는 additive 옵션으로 분리했다.

"통계는 0개 변화"는 이 배치의 M 정의(q/CI 기반)가 자기쌍 비교에서 유의한 변화를 하나도 찾지 못했기 때문(정상 — 자기 자신과 비교하면 실제 통계적 차이가 없어야 한다); 같은 데이터로 ST-11 홈 화면의 `statCount`(status 기반)를 계산하면 212가 나온다는 발산은 위 구현 결정/미확인 사항에 기록했다. `본문 477/6000자`는 파이썬으로 title+description+footer.text+Σ(name+value)를 독립 재계산해 교차 검증했고 동일하게 **477**이 나왔다. `unannounced 0건`은 자기 자신 비교에서 미공지 변화가 0건이라는 뜻으로 파이프라인이 올바르게 동작함을 보여준다(하나라도 나왔다면 버그).

- 미확인 사항:
  - **`/item/{encodeURIComponent(id)}/` 링크가 ST-12의 실제 라우트와 정확히 일치하는지 검증하지 못했다** — ST-12는 동시에 다른 에이전트가 작업 중이라 `generateStaticParams`의 파라미터 인코딩 방식을 확인할 수 없었다. ST-12가 콜론을 다른 방식으로 이스케이프하면 이 배치의 모든 디스코드 링크가 404 난다 — 오케스트레이터가 배치 완료 후 교차 검증 필요.
  - **`DEFAULT_SITE_URL` 자리표시 값**(`https://patchgap.vercel.app`)이 실제 배포 도메인인지 미확인 — SCOPE/README/design 문서 어디에도 확정 문자열이 없었다. 실제 Vercel 배포 후 `--site` 인자나 이 상수를 갱신해야 한다.
  - **네트워크 레벨 오류(DNS 실패·ECONNRESET 등, `fetchImpl`이 reject하는 경우)는 재시도하지 않는다** — 배치 지시가 429/5xx(HTTP 상태 코드)만 재시도 대상으로 명시했고 네트워크 예외는 언급하지 않아, riot-client.ts와 달리 `sendWebhook`은 이 경우 즉시 예외를 전파한다.
  - **`DISCORD_WEBHOOK_URL`이 비어 있어 실제 디스코드 API에 대한 라이브 전송 검증은 여전히 하지 못했다** — 전송 경로(`sendWebhook`→`writeNotifyLog`) 자체는 이번 반영으로 가짜 fetch(204)를 통해 **단위 테스트 수준에서는 실행·검증**됐지만(위 실행 결과), 실제 디스코드 서버가 주는 429 바디 포맷(`retry_after`의 실제 소수 정밀도)·5xx 발생 빈도·타임아웃 특성 등은 목 fetch가 흉내낸 것과 100% 같다는 보장이 없다. 웹훅 URL이 채워지면 `--dry-run` 없이 1회 라이브 전송으로 재검증 권장.
  - **`loadMatchCount`가 `summary.json`의 `data.matches` 필드명에 의존한다** — ST-06 소유 스키마이며, 향후 필드명이 바뀌면 이 함수가 조용히 `null`을 반환해 footer가 `n=?/?`로만 표시된다(크래시하지 않지만 정보 손실).
  - **디스코드 embed의 M(유의 변화 개수)과 ST-11 홈 화면의 M(`statCount`)이 서로 다른 정의라 같은 데이터에서 다른 숫자를 보여준다** — 자기쌍 26.17 실측: 홈 화면 `statCount`(status 기반)는 212, 이 embed의 M(q/CI 기반)은 0. 오케스트레이터가 두 정의 중 하나로 통일할지, 서로 다른 의도(홈=대략적 개요, 알림=엄밀한 통계적 유의성)로 의도적으로 남길지 결정해야 한다.
  - **`data/aggregated/**`가 이 세션 동안 다른 에이전트에 의해 최소 두 차례 삭제·재생성됐다**(구현 결정 참고) — 이 배치의 테스트는 전부 `dataRoot` 임시 디렉토리로 옮겨 이 문제로부터 격리됐지만, B7의 다른 배치(ST-11/12/14)나 오케스트레이터의 최종 통합 검증이 여전히 커밋된 `data/aggregated`의 실제 내용에 의존한다면 같은 방식의 불안정성을 겪을 수 있다 — 최종 통합 시점에 이 디렉토리가 의도한 실데이터로 안정돼 있는지 재확인 필요.
